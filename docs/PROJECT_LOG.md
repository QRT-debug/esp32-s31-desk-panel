## 阶段四：屏幕边缘频闪（11-15，已解决）

排查路径与结论：

| 试过的 | 结果 |
|---|---|
| 单缓冲直写 | 无效 |
| bounce buffer | **更差**（中断里 memcpy 也读 PSRAM） |
| PCLK 25→20→16MHz | 无效 ⇒ 不是带宽/时间余量 |
| 纯黑背景 | 仍闪 ⇒ 不是混色 |
| CPU 满载（纯白静止 + 死循环） | **不闪** ⇒ 不是电源/负载 |
| **`pclk_active_neg = false`** | **明显改善**，用户接受 |

**根因**：CPU 写 PSRAM 抢占 MSPI，打断 RGB DMA（屏无 GRAM，DMA 必须全程不停抽数据）。

## 阶段六：音频（11-16，主线）

### 6.1 硬件核查

- ES8389 + NS4150B×2 + 双 MEMS 麦；I2S 五线全引出（IO2~IO6），PA=IO7；
- 参考 `kmyclab/esp32-s31-korvo1-bringup`：STD TX / 48k / 16bit / **MCLK disabled** / codec slave 可出声。

### 6.2 音频"嘶啦"与屏幕条纹同时出现（已解决）

- 现象：播放时喇叭"老电视雪花嘶啦" + 屏幕中间/右侧彩色条纹；
- 排查：引脚无冲突 → 参考配置一致 → PC 端 FFT 证明 WAV 是音乐；
- **根因：播放时 `fread` 从 flash 读 WAV 打断 RGB LCD DMA（条纹），同时 I2S 默认 DMA 只有 30ms 余量（断流 = 嘶啦）**；
- **解法**：整曲预载 **PSRAM**（2 槽缓存，播放期间零 flash 访问）+ I2S `dma_desc_num` 6→16（80ms）+ 大块播放（4096 帧）。

### 6.3 音量滑块 / 界面三栏

- 手机式大滑块（600px）实时写 ES8389 DAC 音量；起播/停播 30ms 淡入淡出防爆音。

### 6.4 真正的"嘶嘶"（11-16 深夜~11-17 凌晨，已解决）

**排查方法（可复用）：分层切除**

| 诊断档 | 听感 | 结论 |
|---|---|---|
| 静音态（DAC mute、PA 开） | 贴耳才有一点点 | 功放/电源底噪正常 |
| `DIAG: SILENCE`（数据全 0、通路全开） | 干净 | 通路自噪 = 无 |
| `DIAG: SINE 1k` / `SINE 8k` | 纯音、无嘶 | 数据链路、DAC、功放全部正常 |
| `DIAG: RAM MUSIC`（音乐搬到内部 RAM） | **仍然嘶** | PSRAM 无罪 |

**最终结论（两个来源，都在音源侧）**：

1. 之前两首 MIDI 渲染 + 128kbps 的曲子**本身带底噪**（用户在 PC 上播放也有）；
2. 我的转码脚本用了**线性插值重采样**（44.1k→48k、无抗混叠），把噪声底抬高 **15~33dB**：
   `ENTERTN` 原生 **-101.4 dBc** → 转完 **-68.2 dBc**；`BLUEDAN` -91.6 → -76.5。

**解法**：固件与音源统一 **44.1kHz**（MP3 原生采样率），**零重采样**；脚本改为"源≠目标就报错退出"。
换成用户提供的 320kbps 音源后验收：**"贴近耳朵有很小的嘶嘶声，其他比之前好太多"** ⇒ 正常底噪水平。

## 阶段七：两次失败实验（教训，勿重犯）

| 实验 | 结果 | 教训 |
|---|---|---|
| 运行时覆盖 ES8389 分频寄存器到 **32fs**（0x05/06/07/09） | 黑屏 + 巨大噪声 | **不能改正在运行的时钟树**；32fs 分频行在本板不工作 |
| 改驱动 `mclk_fre` 为 **×2（32fs）** | 巨大噪声 + 低频"嗡" | 同上，两次踩同一个坑 |
| I2S 改 **32bit slot** 想把 BCLK 提到 64fs | **播放速度慢一倍**（实测 22.1kHz） | IDF 的 BCLK 仍按 16bit 算，硬件每帧发 64 BCLK ⇒ LRCK 减半 |

**结论**：本板 codec 与 I2S 的时钟差异（BCLK 32fs vs 驱动假设 64fs）**只能靠硬件补 MCLK 解决**（IO2 → R56，标 NC 未贴）。
实测证明这条差异带来的失真远小于音源噪声，**不值得为它动烙铁**。

## 阶段八：烧录提速（11-16）

| 配置 | 纯烧录耗时（1.45MB 固件） |
|---|---|
| 原始：`NO_STUB` + 921600 | **30 s 以上** |
| 开 stub + 921600 | 16.1 s |
| **开 stub + 1500000（现用）** | **12.6 s** |
| 开 stub + 2000000 | 11.3 s（不稳，不采用） |
| 内容无变化（IDF 6.1 增量烧录） | 6.9 s |
| **改一行代码 → 编译 + 烧录** | **18.1 s** |

- 根因：`sdkconfig` 里 `CONFIG_ESPTOOLPY_NO_STUB=y`（历史残留）让 esptool 走最慢的 ROM 路径；
- 已在 `sdkconfig` + `sdkconfig.defaults` 双处修正，`idf_env.ps1` 里 `flash`/`appflash` 固定 1.5M。

## 复盘（写给以后的自己）

- 整晚有 **3 次**让用户"听到大嘶啦被吓到"：两次 32fs、一次 32bit slot；
- **教训**：动 codec 时钟这类高风险改动前，先做零风险测量（如固件内 `DIAG RATE` 自测采样率）；用户在场听音时，不要连续上未验证的配置；
- **有效的做法**：分层切除 + 让用户只回答"有没有声音"（一次一个问题），比堆解释有效得多。
