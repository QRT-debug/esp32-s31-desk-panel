## 阶段四：屏幕边缘频闪（11-15，已解决）

排查路径与结论：

| 试过的 | 结果 |
|---|---|
| 单缓冲直写 | 无效 |
| bounce buffer | **更差**（中断里 memcpy 也读 PSRAM） |
| PCLK 25→20→16MHz | 无效 ⇒ 不是带宽/时间余量 |
| 纯黑背景 | 仍闪 ⇒ 不是混色 |
| CPU 满载（纯白静止 + 死循环） | **不闪** ⇒ 不是电源/负载 |
| **`pclk_active_neg = false`** | **明显改善**，用户接受 |

**根因**：CPU 写 PSRAM 抢占 MSPI，打断 RGB DMA（屏无 GRAM，DMA 必须全程不停抽数据）。

## 阶段六：音频（11-16，主线）

### 6.1 硬件核查

- ES8389 + NS4150B×2 + 双 MEMS 麦；I2S 五线全引出（IO2~IO6），PA=IO7；
- 参考 `kmyclab/esp32-s31-korvo1-bringup`：STD TX / 48k / 16bit / **MCLK disabled** / codec slave 可出声。

### 6.2 音频"嘶啦"与屏幕条纹同时出现（已解决）

- 现象：播放时喇叭"老电视雪花嘶啦" + 屏幕中间/右侧彩色条纹；
- 排查：引脚无冲突 → 参考配置一致 → PC 端 FFT 证明 WAV 是音乐；
- **根因：播放时 `fread` 从 flash 读 WAV 打断 RGB LCD DMA（条纹），同时 I2S 默认 DMA 只有 30ms 余量（断流 = 嘶啦）**；
- **解法**：整曲预载 **PSRAM**（2 槽缓存，播放期间零 flash 访问）+ I2S `dma_desc_num` 6→16（80ms）+ 大块播放（4096 帧）。

### 6.3 音量滑块 / 界面三栏

- 手机式大滑块（600px）实时写 ES8389 DAC 音量；起播/停播 30ms 淡入淡出防爆音。

### 6.4 真正的"嘶嘶"（11-16 深夜~11-17 凌晨，已解决）

**排查方法（可复用）：分层切除**

| 诊断档 | 听感 | 结论 |
|---|---|---|
| 静音态（DAC mute、PA 开） | 贴耳才有一点点 | 功放/电源底噪正常 |
| `DIAG: SILENCE`（数据全 0、通路全开） | 干净 | 通路自噪 = 无 |
| `DIAG: SINE 1k` / `SINE 8k` | 纯音、无嘶 | 数据链路、DAC、功放全部正常 |
| `DIAG: RAM MUSIC`（音乐搬到内部 RAM） | **仍然嘶** | PSRAM 无罪 |

**最终结论（两个来源，都在音源侧）**：

1. 之前两首 MIDI 渲染 + 128kbps 的曲子**本身带底噪**（用户在 PC 上播放也有）；
2. 我的转码脚本用了**线性插值重采样**（44.1k→48k、无抗混叠），把噪声底抬高 **15~33dB**：
   `ENTERTN` 原生 **-101.4 dBc** → 转完 **-68.2 dBc**；`BLUEDAN` -91.6 → -76.5。

**解法**：固件与音源统一 **44.1kHz**（MP3 原生采样率），**零重采样**；脚本改为"源≠目标就报错退出"。
换成用户提供的 320kbps 音源后验收：**"贴近耳朵有很小的嘶嘶声，其他比之前好太多"** ⇒ 正常底噪水平。

## 阶段七：两次失败实验（教训，勿重犯）

| 实验 | 结果 | 教训 |
|---|---|---|
| 运行时覆盖 ES8389 分频寄存器到 **32fs**（0x05/06/07/09） | 黑屏 + 巨大噪声 | **不能改正在运行的时钟树**；32fs 分频行在本板不工作 |
| 改驱动 `mclk_fre` 为 **×2（32fs）** | 巨大噪声 + 低频"嗡" | 同上，两次踩同一个坑 |
| I2S 改 **32bit slot** 想把 BCLK 提到 64fs | **播放速度慢一倍**（实测 22.1kHz） | IDF 的 BCLK 仍按 16bit 算，硬件每帧发 64 BCLK ⇒ LRCK 减半 |

**结论**：本板 codec 与 I2S 的时钟差异（BCLK 32fs vs 驱动假设 64fs）**只能靠硬件补 MCLK 解决**（IO2 → R56，标 NC 未贴）。
实测证明这条差异带来的失真远小于音源噪声，**不值得为它动烙铁**。

## 阶段十一：屏幕边缘随机闪的完整排查（11-21 深夜，未解决 → 指向硬件）

**现象**：屏幕上"四周指不定什么区域"随机闪，烧录后更明显、过一会略好；亮度 100% 仍闪。

### 已排除项（每条都有实测证据，不要再重复试）

| 试过的 | 结果 | 结论 |
|---|---|---|
| 充电宝供电，USB 电流计峰值 **0.4A** | 照样闪 | 排除电源电流/纹波/PC USB |
| 背光亮度拉到 **100%**（PWM 恒高） | 照样闪 | 排除 LEDC 背光 PWM（5kHz/10bit） |
| 关 WiFi | 照样闪 | 排除 WiFi DMA 争用 |
| PCLK **10 / 16 / 20 / 25MHz** | 10MHz **更闪且失真**（低于 HX8264 最低 PCLK，且低帧率让闪更显眼），16/20 无改善 | 排除带宽/时序余量 |
| `pclk_active_neg` **true / false** | 两者都闪（false 略好，保持 false） | 排除采样沿 |
| porch 加大（HBP88→104 等） | **更明显 + 小区域失真** | 排除"留余量"，商家值即最优 |
| `dma_burst_size` 64→128 | **更明显 + 失真**（1600÷128=12.5 半个突发跨行） | 必须保持 64（1600÷64=25 整除） |
| PSRAM **250 / 200MHz** | 都闪 | 排除 PSRAM 速率 |
| LVGL **FULL / DIRECT**（脏区渲染，写入 768KB→7.5KB/帧） | 都闪 | 排除"CPU 写 PSRAM 抢 MSPI"这一总量假设 |
| `esp_cache_msync(C2M)` 按脏区同步 | 调用成功（无报错，证明确为 cacheable），但闪不变 | cache 一致性不是主因 |

### 结论

**软件侧已穷尽**，指向硬件信号完整性。待查三处：

1. **FPC 排线压接**（按压座子看形态是否变化）
2. **PCLK / DATA 是否有串阻 22~33Ω**（没有的话加串阻抑制振铃）
3. **FPC 下方地平面是否完整**（回流路径）

### 教训（跨项目有效）

1. ★★★ **改 `sdkconfig` 的代价被严重低估**：改 PSRAM 频率会让 **1867 个目标全量重编**，每次必撞 `x509_crt.c` 僵死（5~10 分钟白费）。⇒ 能用源码改动解决的，绝不改 sdkconfig；非改不可时，用**时间戳技巧**：把所有 `.obj/.a` touch 到当前、把 `build/config/sdkconfig.h` 改成 1 小时前 → ninja 只编真正改过的源码。
2. ★★ **编译僵死的真根因是杀软**：Defender 排除列表原本只有 `build`、`Temp`、`D:/esp/.espressif`，**漏了源码目录** ⇒ cc1 读头文件被实时扫描锁住，表现为"CPU 时间恒为 0 秒"（不是死循环）。补上项目根目录后，增量编译 12~18 秒。
3. ★ **判断"真编 vs 僵死"只看一个指标**：cc1/gcc 的 **CPU 时间**是否在涨。内存、进度条都不可靠。
4. ★ **改 DMA 参数前先算行宽整除**：每行 800×2 = 1600 字节，burst 必须能整除它。
5. ★ **本机型编译怪癖**：卡在 `x509_crt.c` / `usbh.c` / `libusb_host_uac.a` / bootloader 时，处理办法 = 杀全进程（含 cc1）+ touch 已生成的产物。

### 阶段十一补充：**已修复**一个真实缺陷 —— cache 不一致导致"局部内容错乱"

**现象**：屏幕小部分区域出现**黄色竖线**等不该有的内容，**下次重绘后消失**。
（与"硬件闪"的关键区别：硬件闪是持续/随机的像素错误，不会因重绘而恢复。）

**根因**：帧缓冲分配在 PSRAM（`fb_in_psram = true`），而本芯片支持 **writeback cache**
（`CONFIG_SOC_CACHE_WRITEBACK_SUPPORTED=y`）⇒ CPU 画的像素先留在 CPU cache；
LCD 的 DMA **绕过 cache 直接读 PSRAM** ⇒ 取到旧帧数据。

**本 IDF 版本的坑**：`esp_lcd_panel_rgb.h` 里**只有 `fb_in_psram`，没有 `fb_behind_cache`**
（官方文档提到的这个开关在 S31 分支被移除了），所以**驱动永远不会自动同步 cache**。

**修法**（`components/ui/src/lvgl_port.c` 的 `flush_cb`）：切帧缓冲前手动同步整屏
```c
esp_cache_msync((void *)px_map, LCD_H_RES * LCD_V_RES * 2, ESP_CACHE_MSYNC_FLAG_DIR_C2M);
```
（768000 字节，能被 64 字节 cache line 整除，无需 UNALIGNED）

**验证**：修复前"小区域黄色竖线"可复现；修复后**竖线消失**，屏幕只剩随机闪（硬件项）。

⇒ **教训：PSRAM 上的帧缓冲 + 带 cache 的芯片，必须显式 C2M 同步，否则 DMA 会读到旧数据。**
这类 bug 的特征是"内容错乱但重绘可恢复"，容易误判成硬件。

### 阶段十一补充二：社区/官方方案的适用性核对（11-22）

查 ESP-IDF 官方 FAQ（esp-faq/.../peripherals/lcd.rst）与社区文章后逐条核对：

| 方案 | 适用性 | 依据 |
|---|---|---|
| **XIP on PSRAM**（`SPIRAM_FETCH_INSTRUCTIONS`+`SPIRAM_RODATA`） | ❌ **不适用** | 官方前提是"PSRAM 与 flash 共用 SPI，写 flash 时 PSRAM 被禁用"（ESP32-S3 的坑）；本芯片 `SOC_PSRAM_MEMSPI_IS_INDEPENDENT=1`（**独立总线**），且这两项在本 IDF 的 esp_psram/Kconfig 中不存在 |
| 关 `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP` | ✅ 已关 | 官方建议；查得 `is not set` |
| **Bounce Buffer**（`bounce_buffer_size_px`） | ❌ 已试更差 | 11-15 结论：中断里 memcpy 同样读 PSRAM，边缘更闪 |
| 降 PCLK | ❌ 已试无效 | 20/16/10MHz 全试，10MHz 更糟 |
| `CONFIG_LCD_RGB_RESTART_IN_VSYNC` | 只治"永久漂移" | 对随机闪无效（会降帧率） |
| `CONFIG_COMPILER_OPTIMIZATION_PERF` | ✅ 已开 | 官方建议 |
| `CONFIG_FREERTOS_HZ=1000` | ✅ 已是 1000 | 官方建议 |
| **`CONFIG_CACHE_L1_DCACHE_LINE_SIZE` 64→32** | ⏳ **唯一未试** | 官方："非 Bounce Buffer 模式用 32 字节"。★ 注意：此项影响所有编译单元，**必须全量重编，不能用时间戳技巧**（否则 64/32 混编会崩） |
| 硬件：PCLK/DATA 串阻、地平面、换屏 | ⏳ 待查 | 软件已穷尽后的主方向 |

**关键结论**：S31 的 PSRAM 是独立总线，社区里"RGB 屏花屏 = flash/PSRAM 抢总线"的经典解法在这里**不成立**，
所以问题更可能落在 PCB 信号完整性（并行 16 线 + 25MHz PCLK 的阻抗/回流）。

### ★★★ 阶段十一 结论更正（11-22 中午）——昨晚的"硬件信号完整性"判断是错的

**决定性证据（用户实测）**：
> "一开始不闪，连续用也不会闪，**闪都是我让你写程序、然后一直烧录程序之后才会出现**"

⇒ **闪只在"反复烧录/热复位"之后出现，冷启动（断电上电）从不闪，正常使用完全不闪。**

**真因**：这块 RGB 屏（HX8264）**没有 RST 引脚、也没有命令通道**（配置里 `disp_gpio_num = -1`，
且 RGB 接口本身无命令线）⇒ **面板唯一的复位方式就是断电**。
`esptool --after hard-reset` 只复位了 ESP32 芯片，**面板一直带电、从未复位**
⇒ 内部扫描位置/时序锁存残留 ⇒ 画面边缘闪、局部失真。
反复烧录 = 反复热复位 ⇒ 症状持续；断电重上电 ⇒ 立刻恢复。

**推翻了什么**（这些"排除项"其实都是同一个原因的表现，不是独立证据）：
- 昨晚"10 项排除 ⇒ 指向硬件信号完整性"的结论**作废**；
- 电源/背光/时钟/采样沿/porch/DMA burst/PSRAM 频率/渲染模式——**全部不是原因**，
  所以怎么调都没用（这正好解释了"调哪个参数都没效果"这个反常现象）。

**保留的正确结论**：
- ✅ **cache msync 修复**（黄色竖线/局部内容错乱、重绘可恢复）——这是**真实且独立的 bug**，与热复位无关；
- ✅ 编译僵死根治（Defender 漏源码目录）；
- ✅ porch 加大 / burst 128 会**主动造成**失真（行宽 1600 不整除 128），不要再用。

**对调试流程的要求（写进 flash_sentinel.ps1 的提示）**：
```
烧录完成 → 如屏幕闪烁：拔掉 USB 2 秒 → 重新插上（面板断电复位）
正常使用（冷启动）不受影响，这是调试期特有现象
```

**教训**：★★★ **判断"硬件故障"前必须先问"冷启动是否也复现"**。
本次连续 1.5 小时、烧了 10 多版，全部在"热复位后"的异常状态上做观测，
把"复位不彻底"误判成"PCB 信号完整性"，代价是整晚白费。
**正确的第一问**：断电重上电后还在吗？
