排查路径与结论：

| 试过的 | 结果 |
|---|---|
| 单缓冲直写 | 无效 |
| bounce buffer | **更差**（中断里 memcpy 也读 PSRAM） |
| PCLK 25→20→16MHz | 无效 ⇒ 不是带宽/时间余量 |

## 阶段六：音频（11-16，主线）

### 6.2 音频"嘶啦"与屏幕条纹同时出现（已解决）

- 现象：播放时喇叭"老电视雪花嘶啦" + 屏幕中间/右侧彩色条纹；
- 排查：引脚无冲突 → 参考配置一致 → PC 端 FFT 证明 WAV 是音乐；
- **根因：播放时 `fread` 从 flash 读 WAV 打断 RGB LCD DMA（条纹），同时 I2S 默认 DMA 只有 30ms 余量（断流 = 嘶啦）**；
- **解法**：整曲预载 **PSRAM**（2 槽缓存，播放期间零 flash 访问）+ I2S `dma_desc_num` 6→16（80ms）+ 大块播放（4096 帧）。

### 6.3 音量滑块 / 界面三栏

- 手机式大滑块（600px）实时写 ES8389 DAC 音量；起播/停播 30ms 淡入淡出防爆音。

### 6.4 真正的"嘶嘶"（11-16 深夜~11-17 凌晨，已解决）

**排查方法（可复用）：分层切除**

| 诊断档 | 听感 | 结论 |
|---|---|---|
| 静音态（DAC mute、PA 开） | 贴耳才有一点点 | 功放/电源底噪正常 |
| `DIAG: SILENCE`（数据全 0、通路全开） | 干净 | 通路自噪 = 无 |
| `DIAG: SINE 1k` / `SINE 8k` | 纯音、无嘶 | 数据链路、DAC、功放全部正常 |
| `DIAG: RAM MUSIC`（音乐搬到内部 RAM） | **仍然嘶** | PSRAM 无罪 |

**最终结论（两个来源，都在音源侧）**：

1. 之前两首 MIDI 渲染 + 128kbps 的曲子**本身带底噪**（用户在 PC 上播放也有）；
2. 我的转码脚本用了**线性插值重采样**（44.1k→48k、无抗混叠），把噪声底抬高 **15~33dB**：
   `ENTERTN` 原生 **-101.4 dBc** → 转完 **-68.2 dBc**；`BLUEDAN` -91.6 → -76.5。

**解法**：固件与音源统一 **44.1kHz**（MP3 原生采样率），**零重采样**；脚本改为"源≠目标就报错退出"。
换成用户提供的 320kbps 音源后验收：**"贴近耳朵有很小的嘶嘶声，其他比之前好太多"** ⇒ 正常底噪水平。

## 阶段七：两次失败实验（教训，勿重犯）

| 实验 | 结果 | 教训 |
|---|---|---|
| 运行时覆盖 ES8389 分频寄存器到 **32fs**（0x05/06/07/09） | 黑屏 + 巨大噪声 | **不能改正在运行的时钟树**；32fs 分频行在本板不工作 |
| 改驱动 `mclk_fre` 为 **×2（32fs）** | 巨大噪声 + 低频"嗡" | 同上，两次踩同一个坑 |
| I2S 改 **32bit slot** 想把 BCLK 提到 64fs | **播放速度慢一倍**（实测 22.1kHz） | IDF 的 BCLK 仍按 16bit 算，硬件每帧发 64 BCLK ⇒ LRCK 减半 |

**结论**：本板 codec 与 I2S 的时钟差异（BCLK 32fs vs 驱动假设 64fs）**只能靠硬件补 MCLK 解决**（IO2 → R56，标 NC 未贴）。
实测证明这条差异带来的失真远小于音源噪声，**不值得为它动烙铁**。

## 阶段十一：屏幕边缘随机闪的完整排查（11-21 深夜，未解决 → 指向硬件）

**现象**：屏幕上"四周指不定什么区域"随机闪，烧录后更明显、过一会略好；亮度 100% 仍闪。

### 已排除项（每条都有实测证据，不要再重复试）

| 试过的 | 结果 | 结论 |
|---|---|---|
| 充电宝供电，USB 电流计峰值 **0.4A** | 照样闪 | 排除电源电流/纹波/PC USB |
| 背光亮度拉到 **100%**（PWM 恒高） | 照样闪 | 排除 LEDC 背光 PWM（5kHz/10bit） |
| 关 WiFi | 照样闪 | 排除 WiFi DMA 争用 |
| PCLK **10 / 16 / 20 / 25MHz** | 10MHz **更闪且失真**（低于 HX8264 最低 PCLK，且低帧率让闪更显眼），16/20 无改善 | 排除带宽/时序余量 |
| `pclk_active_neg` **true / false** | 两者都闪（false 略好，保持 false） | 排除采样沿 |
| porch 加大（HBP88→104 等） | **更明显 + 小区域失真** | 排除"留余量"，商家值即最优 |
| `dma_burst_size` 64→128 | **更明显 + 失真**（1600÷128=12.5 半个突发跨行） | 必须保持 64（1600÷64=25 整除） |
| PSRAM **250 / 200MHz** | 都闪 | 排除 PSRAM 速率 |
| LVGL **FULL / DIRECT**（脏区渲染，写入 768KB→7.5KB/帧） | 都闪 | 排除"CPU 写 PSRAM 抢 MSPI"这一总量假设 |
| `esp_cache_msync(C2M)` 按脏区同步 | 调用成功（无报错，证明确为 cacheable），但闪不变 | cache 一致性不是主因 |

### 结论

**软件侧已穷尽**，指向硬件信号完整性。待查三处：

1. **FPC 排线压接**（按压座子看形态是否变化）
2. **PCLK / DATA 是否有串阻 22~33Ω**（没有的话加串阻抑制振铃）
3. **FPC 下方地平面是否完整**（回流路径）

### 教训（跨项目有效）

1. ★★★ **改 `sdkconfig` 的代价被严重低估**：改 PSRAM 频率会让 **1867 个目标全量重编**，每次必撞 `x509_crt.c` 僵死（5~10 分钟白费）。⇒ 能用源码改动解决的，绝不改 sdkconfig；非改不可时，用**时间戳技巧**：把所有 `.obj/.a` touch 到当前、把 `build/config/sdkconfig.h` 改成 1 小时前 → ninja 只编真正改过的源码。
2. ★★ **编译僵死的真根因是杀软**：Defender 排除列表原本只有 `build`、`Temp`、`D:/esp/.espressif`，**漏了源码目录** ⇒ cc1 读头文件被实时扫描锁住，表现为"CPU 时间恒为 0 秒"（不是死循环）。补上项目根目录后，增量编译 12~18 秒。
3. ★ **判断"真编 vs 僵死"只看一个指标**：cc1/gcc 的 **CPU 时间**是否在涨。内存、进度条都不可靠。
4. ★ **改 DMA 参数前先算行宽整除**：每行 800×2 = 1600 字节，burst 必须能整除它。
5. ★ **本机型编译怪癖**：卡在 `x509_crt.c` / `usbh.c` / `libusb_host_uac.a` / bootloader 时，处理办法 = 杀全进程（含 cc1）+ touch 已生成的产物。

### 阶段十一补充：**已修复**一个真实缺陷 —— cache 不一致导致"局部内容错乱"

**现象**：屏幕小部分区域出现**黄色竖线**等不该有的内容，**下次重绘后消失**。
（与"硬件闪"的关键区别：硬件闪是持续/随机的像素错误，不会因重绘而恢复。）

**根因**：帧缓冲分配在 PSRAM（`fb_in_psram = true`），而本芯片支持 **writeback cache**
（`CONFIG_SOC_CACHE_WRITEBACK_SUPPORTED=y`）⇒ CPU 画的像素先留在 CPU cache；
LCD 的 DMA **绕过 cache 直接读 PSRAM** ⇒ 取到旧帧数据。

**本 IDF 版本的坑**：`esp_lcd_panel_rgb.h` 里**只有 `fb_in_psram`，没有 `fb_behind_cache`**
（官方文档提到的这个开关在 S31 分支被移除了），所以**驱动永远不会自动同步 cache**。

**修法**（`components/ui/src/lvgl_port.c` 的 `flush_cb`）：切帧缓冲前手动同步整屏
```c
esp_cache_msync((void *)px_map, LCD_H_RES * LCD_V_RES * 2, ESP_CACHE_MSYNC_FLAG_DIR_C2M);
```
（768000 字节，能被 64 字节 cache line 整除，无需 UNALIGNED）

**验证**：修复前"小区域黄色竖线"可复现；修复后**竖线消失**，屏幕只剩随机闪（硬件项）。

⇒ **教训：PSRAM 上的帧缓冲 + 带 cache 的芯片，必须显式 C2M 同步，否则 DMA 会读到旧数据。**
这类 bug 的特征是"内容错乱但重绘可恢复"，容易误判成硬件。

查 ESP-IDF 官方 FAQ（esp-faq/.../peripherals/lcd.rst）与社区文章后逐条核对：

### ★★★ 阶段十一 结论更正（11-22 中午）——昨晚的"硬件信号完整性"判断是错的

**决定性证据（用户实测）**：
> "一开始不闪，连续用也不会闪，**闪都是我让你写程序、然后一直烧录程序之后才会出现**"

⇒ **闪只在"反复烧录/热复位"之后出现，冷启动（断电上电）从不闪，正常使用完全不闪。**

**真因**：这块 RGB 屏（HX8264）**没有 RST 引脚、也没有命令通道**（配置里 `disp_gpio_num = -1`，
且 RGB 接口本身无命令线）⇒ **面板唯一的复位方式就是断电**。
`esptool --after hard-reset` 只复位了 ESP32 芯片，**面板一直带电、从未复位**
⇒ 内部扫描位置/时序锁存残留 ⇒ 画面边缘闪、局部失真。
反复烧录 = 反复热复位 ⇒ 症状持续；断电重上电 ⇒ 立刻恢复。

**推翻了什么**（这些"排除项"其实都是同一个原因的表现，不是独立证据）：
- 昨晚"10 项排除 ⇒ 指向硬件信号完整性"的结论**作废**；
- 电源/背光/时钟/采样沿/porch/DMA burst/PSRAM 频率/渲染模式——**全部不是原因**，
  所以怎么调都没用（这正好解释了"调哪个参数都没效果"这个反常现象）。

**保留的正确结论**：
- ✅ **cache msync 修复**（黄色竖线/局部内容错乱、重绘可恢复）——这是**真实且独立的 bug**，与热复位无关；
- ✅ 编译僵死根治（Defender 漏源码目录）；
- ✅ porch 加大 / burst 128 会**主动造成**失真（行宽 1600 不整除 128），不要再用。

**对调试流程的要求（写进 flash_sentinel.ps1 的提示）**：
```
烧录完成 → 如屏幕闪烁：拔掉 USB 2 秒 → 重新插上（面板断电复位）
正常使用（冷启动）不受影响，这是调试期特有现象
```

**教训**：★★★ **判断"硬件故障"前必须先问"冷启动是否也复现"**。
本次连续 1.5 小时、烧了 10 多版，全部在"热复位后"的异常状态上做观测，
把"复位不彻底"误判成"PCB 信号完整性"，代价是整晚白费。
**正确的第一问**：断电重上电后还在吗？

## 11-22 二次更正：频闪真因是 **LVGL 双缓冲同步拷贝没做 cache 写回**（软件 bug，不是复位/硬件）

**用户新线索（推翻上一条的"热复位"定性）**：
> "其实断电以后连上也闪，好像一定要**闪着运行一段时间**或者**很长时间断电一段时间**才能不频闪"

⇒ 上一条"冷启动从不闪"的说法不成立。但也不用再找硬件了 —— **代码里有一个必然发生的 bug**。

### 证据链（代码级，可复现）

1. LVGL 在 **DIRECT + 双缓冲**下，每帧渲染前调 `refr_sync_areas()`（`src/core/lv_refr.c:675`），
   用**纯 CPU `lv_draw_buf_copy()`**（`lv_draw_buf.c:402` → `buf_copy_cb` memcpy）
   把**上一帧的脏区**从"正在扫描的那块 fb"拷到"即将渲染的那块 fb"。
2. 帧缓冲在 PSRAM 且 cacheable（`fb_in_psram = true`）。CPU 的写入先落在 **CPU cache**；
   LCD 的 DMA **绕过 cache** 直读 PSRAM。
3. 而 `flush_cb` 原来只对**本帧 `area`** 做 `esp_cache_msync`。
   **被 `refr_sync_areas` memcpy 过的区域根本不经过 flush 回调** ⇒ 永远 sync 不到。
4. 结果：那块区域 DMA 读到的是**两帧以前的旧像素**，下一帧再被覆盖
   ⇒ 肉眼看到"**某片区域闪一下**"，位置随脏区跑。

### 为什么能解释全部既有观察

| 观察 | 解释 |
|---|---|
| "四周指不定什么区域频闪" | 脏区在哪、就哪块闪；位置随机 |
| 烧录后 / 刚上电最明显 | 重绘量最大，sync 拷贝最多 |
| "闪一阵就好" | 界面静止后 LVGL 不再刷新、不切 fb，`refr_sync_areas` 不执行 |
| "断电很久再插就不闪" | 离开一阵回来，界面早已静止 —— **不是断电的功劳** |
| 进 System 关 WiFi 仍闪 | System 页自己在刷 CPU/内存数字 |
| 之前"降 PSRAM 200M 无效" | **假结论**：`sdkconfig.defaults` 里 `SPIRAM_SPEED_250M` 与 `200M` 同时 `=y`，IDF 以已有 `sdkconfig` 为准 ⇒ 那次实验**从未生效**，一直跑 250M |

### 修复

- `components/ui/src/lvgl_port.c`：flush_cb 记账本帧脏区；`flush_is_last` 时**同时 sync

  直流偏压，液晶极化后会局部闪）。

- 删掉 flush 路径上"每 30 帧一条 ESP_LOG"（UART 输出会阻塞刷新，实测 flush 6ms → 1ms）。
- `sdkconfig.defaults`：删掉冲突的 `CONFIG_SPIRAM_SPEED_200M=y`，保持 250M。

## 11-22 最终定性：边缘频闪 = VCOM 型 flicker，帧率 48.5Hz 太低；提到 64Hz 解决

### 用户两条决定性描述（把方向从软件彻底拉回面板）

1. > "内容一直都不动、只有亮度在抖" —— 排除全部刷新路径（cache / 双缓冲 / PSRAM / PCLK 相位）
2. > "**屏是矩形的，矩形的四个边缘在闪，不一定哪几个边，指不定每次是哪几个**，很快数不清"
   - "只有亮度抖" ⇒ 液晶两端电压没变，是**光照**在变 或 **VCOM** 在抖
   - "只在**边缘**、且随机是哪几个边" ⇒ **边缘像素没有邻接像素，寄生电容与中心不同**，
     同样的 VCOM 偏差在中心看不出来、在边缘最明显 ⇒ **典型 VCOM flicker**
   - "很快数不清" ⇒ 40~60Hz 量级 ⇒ 正好等于当时帧率 **48.5Hz**

**反向证据（此前被误读为"无改善"）**：10MHz 时 `19.4fps` 表现为"**更闪且失真**"；
20/16MHz（38.8/31.0fps）也只是"没变好"。**帧率越低越闪** ⇒ 是 flicker，不是信号完整性/时序余量。

### 解法：把帧率顶过临界闪烁频率

`LCD_PCLK_MHZ` 25 → **33**，976×528 总周期 = **64.0fps**（超商家验证值 32%，实测无白条）。
**结果：肉眼完全看不出闪**，只有手机录像能拍到右下角一小块低频调制。

### 手机能拍到、眼睛看不到的两个原因（都不需要再改）

1. **CMOS 逐行曝光（rolling shutter）**会放大任何周期性亮度调制，人眼没有这个效应；
2. **5 kHz 背光 PWM 与 64 Hz 帧率的拍频 = 8 Hz**（5000 − 78×64 = 8），正是"闪得比较慢"的节奏。
   幅度低于视觉阈值，可忽略。★ 若将来一定要 PWM 调光，拍频无法用"换频率"规避——
   64Hz 的间距只有 64，拍频上限仅 32Hz，永远落在可见区。

### 顺带查实的独立问题：背光 5kHz PWM 把升压恒流斩废了

用户报告"改成 duty 100% 后**明显变亮**"⇒ 75% 时实际亮度远低于 75%。
4.3" 多串背光（Vf 12~15V）模组内是**升压恒流**，软启动毫秒级；5kHz（200µs 周期）斩 EN
⇒ 每次都没充到位就开始放电 ⇒ 亮度不足 + 输出电流摆动。
★ 但**闪烁不是它造成的**（100% 恒定后照旧闪）——两件事必须分开归因。
正式方案：背光常亮；若必须调亮度，需硬件在 BL_CTR 上加 RC 滤波（模拟调光）或改驱动。

### 这一轮之前的所有"排除结论"重新归类

| 排查项 | 结论 |
|---|---|
| PCLK 25/20/16/10 MHz | ❌ 当时只看"闪不闪"，没看**频率变化**。恰恰是频率的证据 |
| porch 加大 / burst 128 | ❌ 会**主动造成**行错位失真，商家值就是最优，别再动 |
| PSRAM 250M→200M | ❌ 从未生效（defaults 里两行 `=y` 冲突），且与亮度无关 |
| `pclk_active_neg` true/false | ❌ 与 flicker 无关 |
| DIRECT/FULL、cache msync | ⚠️ cache 不一致是**真实独立 bug**（黄色竖线/局部错乱），已修，但**不是频闪原因** |
| "热复位导致面板没复位" | ❌ 错误方向；面板复位与此无关 |

**教训**：★★★ **"闪"必须先分清是「内容错乱」还是「亮度波动」。**
若一开始就问"画面内容有没有错、还是只是明暗在变"，第 2 小时就能定到 VCOM/帧率，
而不是花两天把 PCLK、porch、burst、PSRAM、渲染模式全试一遍。
**亮度类症状的物理链路只有三条**：光照（背光）、VCOM/像素电压、电源纹波 —— 与刷新路径正交。

## 11-22 终局：40MHz + 1120×576 + pclk_active_neg=true —— 三条硬约束的唯一解

用户最终确认：**"好像都没了"**（无边缘闪、无波浪、无白竖线、无抖动）。

### 完整因果链（每个现象对应一个独立约束，不要混为一谈）

| 现象 | 触发条件 | 真因 |
|---|---|---|
| 四个边缘 **flicker**（很快数不清） | 帧率 48.5Hz | VCOM 型。边缘像素无邻接、寄生电容与中心不同 ⇒ 同样 VCOM 偏差在中心看不出、边缘最明显。**10MHz(19.4fps) 时"更闪"即为反证：帧率越低越闪** |
| 文字 **波浪** | PCLK 32MHz | `lcd_hal_cal_pclk_freq()` **固定 mo=2**，实际分频是 `160/(n+b/a)/2`。32MHz ⇒ lcd_clk 64MHz ⇒ `160/64 = 2.5` 小数分频，PCLK 周期在 25/37.5ns 交替（±20%） |
| 画面 **抖动** + render 49ms | 40MHz + 小 porch | 有效区占 74.5%，DMA 连轴转，CPU 访问 PSRAM 持续被仲裁延迟，render 24ms→49ms（19~41fps 摆） |
| 右侧 **白竖线** 1~2px | 40MHz + `pclk_active_neg=false` | 超规格压缩建立/保持裕量，行尾采错。换 true 后消失 |
| 亮度整体偏暗 | `backlight_set(75)` | 5kHz PWM 斩模组内升压恒流（软启动毫秒级 vs 200µs 周期），没充到位。改 100% 后"明显变亮" |

### 死结与绕法（这是本轮最核心的推理）

**死结**：零抖动 PCLK 只有 `160/(2×PCLK)` 为整数的档位 ⇒ **40 / 26.67 / 20 MHz**，
对应帧率 77.6 / 51.7 / 38.8Hz —— **中间没有 60~65Hz 的选项**，而 60Hz 又是 flicker 的硬门槛。

**绕法**：**帧率 = PCLK ÷ (H_total × V_total)**，帧率不必等于 PCLK 的极限。
保持 PCLK 40MHz（零抖动），把总周期撑到 **1120×576** ⇒ **62.00fps**。
副作用是有效区只占 59.5% ⇒ **反而给 DMA 留出 40% 空闲，把 render 从 49ms 救回 24ms**。
一个改动同时解决"太高"和"太慢"两个看似矛盾的问题。

### 附带纠正的两条错误结论

1. **"加大 porch 会导致失真"** ❌ —— 当时 HBP/HFP 改成 104/56 ⇒ H_total 1008 ⇒ `1008×2 = 2016`，
   `2016÷64（DMA burst）= 31.5` 不整除 ⇒ 突发跨行错位。**porch 本身可以加，前提是 H_total 让行宽能被 64 整除。**
2. **"32MHz 是 160 的 1/5 所以零抖动"** ❌ —— 看错了对象。要看 `160/(2×PCLK)` 而不是 `160/PCLK`，
   因为 IDF 硬编码 `mo=2`（源码注释：*due to some unstable hardware issue, we prefer to start with mo=2 first*）。

### 最终配置（改动前先读 HARDWARE.md 第 2 节的约束表）

```
PCLK 40MHz · H_total 1120 (800+48+160+112) · V_total 576 (480+3+48+45)
⇒ 62.00 fps · pclk_active_neg = true · dma_burst_size 64
实测：46 FPS / render 24ms / flush 5~11ms / CPU 5~8%
```

⚠️ 40MHz 超商家验证值（25MHz）**60%**，实测可用但余量薄。退路顺序：**32MHz（不闪、轻微波浪）**，
**不要退 25MHz**（flicker 立刻回来）。

### 教训

★★★ **一个"闪"字底下可能同时压着 3~4 个互不相关的硬约束。** 本轮依次解开的是：
帧率→flicker、分频比→波浪、DMA 占用→抖动、采样沿→白竖线、PWM 斩升压→亮度。
**每解开一个都会暴露出下一个**，因为前一个把其他症状盖住了。
⇒ 正确姿势不是"找一个总原因"，而是**每次只留一个变量、把现象归因到具体物理量**（帧率/分频比/带宽/采样沿）。

### 11-22 追加：62Hz → **66Hz**（帧率下限由亮度决定）

62Hz 版上线后用户报告"**又有频闪**"。原因不是时序错，而是**临界闪烁频率 CFF 随亮度上升**：
背光诊断改到 100% 后画面更亮，CFF 抬高 ⇒ 62Hz 落在临界线上，主观时有时无。

用户实测的三个锚点（都在 100% 亮度下）：
- **62Hz → 又会闪**（不可接受）
- **64Hz → "几乎看不出来"**（勉强，仍是临界边缘）
- **66Hz → 取 6% 余量**

改法只动 V_total：**576 → 541**（垂直消隐 96 → 61 行），
`40e6 / (1120 × 541) = 66.02fps`；有效区占比 59.5% → 63.4%，DMA 空闲 40% → 36.6%，
`render` 实测仍 24ms（36.6% 够用）。

**教训**：★★ 帧率够不够不是绝对值，**是亮度、视角、疲劳程度的函数**。
定帧率下限必须绑定当时的背光档位；本板背光被 PWM 斩到"只能 100% 或很暗"，所以只能靠提帧率解决。

## 11-22 软件架构：运行时配置层（NVS）上线

**动机**：WiFi 凭据、PC 中转地址、城市原本全是编译期宏（`wifi_config.h`），
换网络就得改代码重烧；同一份固件无法发给不同的人。这是"能不能交付"的分水岭。

### 做法

新增 `components/netapp/{include,src}/app_cfg.{h,c}`：

```c
typedef struct {
    uint16_t ver;              /* 结构版本，字段变动 +1，旧 blob 自动回落默认值 */
    char     wifi_ssid[33], wifi_pass[65];
    char     city[24];         /* 空 = 按公网 IP 自动定位（wttr.in 默认行为） */
    char     pc_host[40]; uint16_t pc_port;
    uint8_t  backlight; int8_t tz; uint8_t theme;
} app_cfg_t;
```

- **整个结构体存一个 NVS blob**（ns `appcfg` / key `cfg`）。不逐项存：
  配置项会随功能增长，逐项存要维护一堆 key 和"缺项怎么办"的分支。
- `wifi_config.h` 降级为**首次上电 / 恢复出厂的默认值** ⇒ 现有设备行为完全不变。
- 接入点三处：`wifi_sta.c`（SSID/密码，密码空则自动降为 OPEN）、
  `pc_monitor.c` 与 `bili_hot.c`（共用同一组 PC 中转地址）。
- `main.c` 在 `nvs_flash_init()` 之后、`lcd_init()` 之前调用 `app_cfg_init()`。

### 验证（实测日志）

```

I (1221) appcfg: ssid="MY_WIFI" pass=*** city="(auto by IP)" pc=192.168.1.2:8080 bl=75% tz=+8 theme=0
I (5449) wifi: connecting to "MY_WIFI" ...
I (5452) pcmon: polling http://192.168.1.2:8080/api/stats.txt every 1000 ms
I (7083) wifi: got ip 192.168.1.3
```
⇒ 三处下游确认走的是 NVS 配置，不是宏。

### 三个编译期坑（记下来）

1. **`SRC_DIRS` 用 CMake glob，新增 .c 必须 `idf.py reconfigure`**，否则链接期
   `undefined reference to app_cfg_init` —— 报错长得像"函数没写"，实际是"文件没进构建"。
2. **netapp 的 REQUIRES 要加 `nvs_flash`**，否则 `nvs.h: No such file or directory`。

   用 `strncpy` 触发 `-Werror=stringop-truncation` ⇒ **用 `strlcpy`**（语义正确且不告警）。

### 11-22 数据缓存：断网也有画面、开机瞬间就有内容

⇒ 所有 save 都放在 **①锁外 ②"数据已到、界面还没更新"的间隙**——此刻画面是静止的，看不出来。

### 11-22 配网 AP 模式修正：按 STA 状态选 AP / APSTA

**踩到的现象**：日志明确打出 `prov: AP "SmartPanel-1624" up`，
但电脑 `netsh wlan show networks` 扫十个网络里**没有它**。

**根因（ESP32 已知限制）**：`WIFI_MODE_APSTA` 下 AP 与 STA **共用一个 radio 且必须同信道**。
STA 连不上时会在 1~13 信道反复扫描，**AP 的 beacon 被反复打断** ⇒ 客户端扫不到。
而配网场景恰好就是"STA 连不上"，最坏组合。

**修正**：
```c
wifi_mode_t mode = wifi_sta_connected() ? WIFI_MODE_APSTA : WIFI_MODE_AP;
```
- 已联网改配置 → APSTA（不断网）
- 未联网自助 → **纯 AP**（无 STA 抢 radio，广播稳定）

**★ 未在离线态实测**：烧录完时用户已把密码改回、设备一直在线，
改动的原理依据充分但没有现场验证。下次真正断网时再看一次。

### 顺带澄清两个误判（避免以后重走）

1. **"无线局域网接口电源关闭"不等于 radio 被关**。
   `netsh wlan show interfaces` 显示 `Radio status: Hardware On / Software On`，
   当次报错是瞬时/调用问题。**判据要用 `show interfaces`，不是看 `show networks` 的报错。**
2. **`netsh wlan show networks` 返回的是缓存**，Windows 约 60s 才真扫一次
   （连续两次一次 10 个网络、一次 6 个即为证据）。
   ⇒ **不能用它判断"AP 有没有广播"**，要结合设备端日志或手机实际连接结果。

### 11-23 01:50 屏保时钟 + SD 壁纸：五连坑复盘（全部实测定位）

最终形态：System 页绿色 CLOCK 按钮 → SD 随机壁纸（硬件 JPEG 解码）+ 96px 等宽时间胶囊，

**五个坑，按发现顺序（每个都曾表现为"卡死"，实际各不相同）：**

1. **渲染驱动模式**：本项目 LVGL 是"每个场景在 draw 里调 `lvgl_port_task()`"驱动的
   （它跑 `lv_timer_handler` = 定时器+渲染+flush）。scene_clock 漏了这行 ⇒
   **LVGL 从不被驱动，屏幕永远停在上一帧**。症状是"卡死"，实际是画面没换过——
   心跳日志证明芯片和对象树全程正常。★ 新场景必查这一行。

2. **场景切换清理惯例**：`ui_goto_scene` 只改索引，**各场景 frame==0 自己调
   `lv_obj_clean(lv_scr_act())`**。漏了 ⇒ 旧页对象盖在新页上——"卡死在 System、
   点哪都没反应"，其实 System 的按钮还在吃点击。★ 九个场景九个 clean，新场景照抄。

3. **LVGL 线程安全**：解码放独立任务后，用 `lv_async_call` 通知 → **死锁**
   （它也进 LVGL 内部队列，从别的线程调就是雷）。正确模式：任务只写
   `volatile s_wp_ready`，LVGL 定时器 100ms 轮询、主上下文更新。

4. **JPEG 硬件解码的缓冲对齐**：2D-DMA 要求 **16 字节对齐**（地址和 size 都要），
   普通 `heap_caps_malloc` 不保证 ⇒ `ESP_ERR_INVALID_ARG`。必须用
   `jpeg_alloc_decoder_mem(size, {buffer_direction}, &alloc_sz)`（输入输出都是）。

5. **大图层级**：壁纸 lv_image 异步创建天然在**顶层**（盖住时间胶囊）；
   `move_background` 又会压到**不透明 bg 的下面**（壁纸整个被盖，只剩灰屏）。
   正确位置 = **`lv_obj_move_to_index(img, 1)`**：bg(0) 之上、胶囊之下。

**已排除的假说（别再走回头路）：**
- ~~esp_cache_msync(INVALIDATE) 必须做~~：官方示例**解码后不做任何 msync**，
  S31 的 2D-DMA 写 PSRAM 硬件保证一致性；对 768KB 做 INVALIDATE 反而曾疑似死锁（已删）。

### 11-23 02:35 ★★★ 重大工具修正：watch_log 打开串口 = 复位设备（"掉电"结论推翻）

**现象**：每次用 `watch_log.py` 抓日志，日志开头必有 `rst:0x1 (POWERON)`——
**不是设备自己重启，是抓日志这个动作触发的复位**，崩溃现场（panic/backtrace）每次都被毁。

**根因**：ESP32 的 auto-download 电路靠 **DTR/RTS 同时翻转**触发复位；
pyserial `open()` 瞬间 Windows 驱动默认拉高 DTR/RTS ⇒ 打开串口 = 复位脉冲。
原脚本把 `dtr=False/rts=False` 放在 **open() 之后**——晚了，脉冲已发出。

**修复**：pyserial 支持在 open() **之前**设置（写入 DCB：DTR/RTS_CONTROL_DISABLE），
open 时电平不变化 ⇒ 无复位脉冲。修复后实测：日志开头无 rst，设备连续运行 2 分半无中断。

**被推翻的结论（都是这个误判的下游）**：
- ~~"上传壁纸时电流峰值掉电"~~ ——那次"重启"就是抓日志复位。供电问题未证实，勿再引用。
- ~~"点 CLOCK 崩溃重启循环"~~ ——LVGL 冻结（页面没驱动）是真问题，但"循环"里的每次
  "重启"都是抓日志复位。真 panic 从未被抓到过。
- "面板残影（重启后屏幕还挂旧帧）"——需重新验证：之前看到的"旧帧"可能只是
  复位后的过渡画面。

**教训**：调试工具自身改变被调试对象的行为 = 观察者效应。抓"当前状态"类日志
（watch_log）必须零扰动；只有抓"启动现场"（catch_boot）才允许主动复位。

### 11-23 03:25→03:35 轻点不灵：真根因是时钟页 hold_ms=1000（触摸处理 1 秒一跳）

**最终定论（已实测验证）**：时钟页场景表 `hold_ms=1000` ⇒ LVGL 的触摸事件处理

### 11-23 17:35 ★★★ 语音识别根因：codec 分频按 4.096MHz 配、实际主时钟只有 512kHz（差 8 倍）

**症状链**：点 TALK 说话 → 服务端收到完整音频（2.5s / 82KB）→ 识别全错
（"测试一下" → "呵呵,遇到"/"法庭主席"/"这就是鱼"）→ 屏幕显示为矩形方框。

**排查过程（全部用客观数据，不靠猜）**：
1. **加 `/voicedbg` 下载接口**把 SD 上的真实录音取到 PC（`voice.c` 每次录音存
   `/sdcard/voice_last.wav`）——从此不用靠"识别结果"间接猜。
2. **波形分析**（画 BMP 用 ViewImage 看）：包络正常（前静音 / 中间 4 个音节爆发 /
   尾部静音）、无削波、无周期性断裂 ⇒ **录音内容本身是对的，不是拾音失败**。
3. **频谱分析**：`0-600Hz 占 82.7%`，`1200-2400Hz 仅 5.1%` ⇒ **辅音高频几乎全丢**。
   这解释了"听上去像被子蒙着嘴"（用户原话）和 ASR 只能瞎猜。
4. **排除法**：变速 0.6~2.0 全扫（无一档能识别）、预加重 k=0.7/0.9/0.97、
   高通 200/400Hz、频谱倾斜 ±12~30dB（结果飘忽"这就是鱼的"/"这就是一个人"）
   ⇒ **不是简单采样率偏差，也不是单纯频响，是数据本身被窄带滤波毁了**。

**根因**：`audio_player.c` 的 `adc_manual_init()` 照抄厂商 `coeff_div` 的
**ratio=256 行**（该行前提是 MCLK=4.096MHz）。但本板 **MCLK 脚未接（R56 标 NC）**，
codec 只有 **BCLK = 32×16k = 512kHz** 当主时钟 ⇒ 分频比错 **8 倍**
⇒ ADC 数字滤波器带宽被设成 `16k/8 = 2kHz`，截止约 900Hz。

**修复**：改用 **ratio=32 行**（`coeff_div[0]`）的分频+滤波值：
`0x05=57 0x06=84 0x07=D0 0x08=03 0x09=C1 0x0A=B0`、
MCLK divider `0x0C/0x0D = 32`（原 256）、`0x43=01`、`0x16=09 0x18=19 0x19=07`。
`512kHz ÷ 32 = 16kHz` 与 I2S LRCK 一致，滤波器回到 16k 带宽。

**实测结果**（同一句"测试一下"）：
| 频带 | 修复前 | 修复后 |
|---|---|---|
| 0-600Hz | 82.7% | 63.1% |
| 600-1200Hz | 7.6% | **22.2%** |
| 1200-2400Hz | 5.1% | **11.7%** |

faster-whisper 直接识别：**`测试一下`** ✔（修复前是"呵呵,遇到"）。

**★ 教训（跨项目）**：**"能出声"≠"时钟对"**。播放路径人耳容错度高，分频错 8 倍也
只是音色变闷；**录音对带宽极敏感，同一个错直接把可用性摧毁**。凡是"codec 无 MCLK、
用 BCLK 当主时钟"的板子，配置表必须按**实际**主时钟选行，不能照抄带 MCLK 的例程。

**同时修掉的两个真 bug**：
- **录音通道逐块重判**：`audio_rec_read_mono` 每 64ms 重新选"能量大的声道"，两路接近时
  通道跳变 ⇒ 音频被切成两段不同信号。改为**首次有信号即锁定**（`audio_rec_begin()` 重置），
  日志打 `rec channel locked to L/R`。
- **`s_peak_rms` 跨次累计**（函数内 static 不清零）⇒ 峰值日志完全失真。改为每次录音清零。

**调试设施（保留）**：`/sdcard/voice_last.wav` 每次录音自动存档；配网页
`GET /voicedbg` 一键下载；`voice.c` 打 ASR 结果字节（查 UTF-8 截断用）。

### 11-23 17:42 中文标点全缺：GB2312 一级汉字库不含符号区

**症状**：语音识别结果"测试一下。"末尾的句号显示成矩形方框（识别本身已正确）。
**根因**：cn18 四块字库是 **GB2312 一级汉字（3755 字）**，而**中文标点在 GB2312 里属于
符号区（区位 1-9），不在一级汉字内** ⇒ `。，、；：？！…—` 全部没有字形。
逐字验证：7 个常用中文标点**全部缺失**（不只是句号）。天气描述/日志带标点同样会变方框。

**修复**：新增 `ui_font_cn_punct`（18px，含 ，。、；：？！""''（）【】《》〈〉…—～·￥％℃），
挂到 fallback 链最末端（`ui_font_cn18d.fallback = &ui_font_cn_punct`）。
**体积代价 7KB**（源码 50KB，编译后约 7KB）——符号字形简单，比汉字便宜得多。

**★ 通用教训**：生成中文字库时 **`--symbols`/`--range` 必须把标点符号一起带上**，
否则"汉字都有、标点全方框"。GB2312 一级汉字 ≠ GB2312 全集。
